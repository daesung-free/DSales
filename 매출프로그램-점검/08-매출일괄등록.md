## 🔴 결함 ① 금액 공식이 발주처 확정과 다릅니다

`api.ts:641`:
```ts
const amount = Math.round((price * supRate) / 100) * qty      // 단가 반올림 후 곱
```

정본 `shared/money.ts:33`:
```ts
export function supplyAmountOf(price, supRate, qty) {
  return Math.floor((price * supRate) / 100 * qty)            // 버림
}
```

**이 화면만 정본을 안 쓰고 자체 계산합니다.** 그리고 그 자체 계산이 하필
**2026-08-06 발주처 확정으로 폐기된 옛 공식**입니다.

CLAUDE.md §8:
> 금액 반올림도 **버림**으로 확정됐습니다(**예전엔 단가 반올림 후 곱**).

### 실제 차이

| 정가 12,345 · 공급률 75% · 수량 150 | 금액 |
|---|---|
| 일괄등록 (현재) | **1,388,850** |
| `money.ts` 정본 (버림) | **1,388,812** |
| 차이 | **+38원** |

한 건에 38원이지만 **일괄등록은 수백 건을 한 번에 넣는 화면**입니다. 그리고 이렇게 들어간
매출이 통합매출조회·매출액정리·순매출·계산서신고로 그대로 흘러갑니다.

**조치**: `supplyAmountOf()` 를 import 해서 쓰면 끝. CLAUDE.md §5 가 명시한
*"규칙을 바꾸면 화면이 아니라 여기부터 고치세요"* 원칙 위반 사례입니다.

## 🔴 결함 ② 마스터 대조를 전혀 안 합니다

`api.ts:636~639` 검증 전부:
```ts
if (!custName)  problems.push('거래처명 누락')     // 빈 문자열만
if (!catName)   problems.push('분류명 누락')       // 빈 문자열만
if (qty <= 0)   problems.push('수량 오류')
if (supRate<0)  problems.push('공급률 오류')
```

**실재 여부를 확인하지 않습니다.** 실제 테스트:

```
존재하지않는거래처 | D.ARCHIVE 국어 | SET | 10 | 75% | 112,500 | 정상 ✓
```

거래처 마스터에 없는 이름인데 **「정상」으로 통과**했습니다.

같은 저장소의 12열 업로드(`uploadParse.ts`)는 정반대로 돼 있습니다:
> **코드 매칭 실패 행은 오류로 표시하고 유효 행만 등록.**

**이름 기반 매칭인데 매칭 검증이 없다**는 게 문제의 핵심입니다. 실서버 연결 시 FK 오류가 나거나,
더 나쁘게는 유사명 거래처에 잘못 붙습니다.

## 🔴 결함 ③ 정가를 마스터에서 안 찾고 15,000 을 씁니다

`api.ts:634`:
```ts
const price = Number(priceRaw) || 15000       // 정가 미입력 시 하드코딩
```

실측 확인 — 샘플 1행 `강남대성, D.ARCHIVE 국어, 시즌1 SET, 150, 75`:

| | 정가 | 금액 |
|---|---|---|
| 화면 표시 | (15,000 가정) | **1,687,500** |
| 마스터 실제값 (`reference.ts:116`) | **36,000** | **4,050,000** |

**2.4배 차이입니다.** 도서 마스터에 정가가 있는데(다른 화면은 다 쓰고 있음) 이 화면만
안 찾습니다. 주석에 *"정가 미입력 시 15000 가정 — 목업"* 이라 적혀 있어 **의도된 임시값**이지만,
화면이 「정상 ✓」 판정과 함께 금액을 확정 표시하므로 **사용자는 맞는 값으로 믿습니다.**

## ⚠️ 매출 일괄 입력 경로가 2개이고 양식이 다릅니다

| 경로 | 양식 | 매칭 | 백엔드 계약 |
|---|---|---|---|
| `/sales/bulk` 매출일괄등록 | **6열** (거래처명·분류명·도서명·수량·공급률[·정가]) | **이름** | ❌ 없음(추론) |
| `/sales/entry` [파일 업로드] | **12열** (`uploadParse.ts`) | **코드**(분류+도서) | ✅ `SalesUploadService` 일치 |

12열 쪽은 CLAUDE.md §4.6.15 가 *"백엔드와 완전히 일치. **바꾸지 마세요**"* 로 못박은 계약이고,
6열 쪽은 *"기획서에 상세 양식이 없어 붙여넣기 기반으로 **구조를 추론**했습니다"* 로 열려 있습니다.

**사용자 입장에선 같은 「매출 일괄 입력」인데 화면마다 양식·검증 강도가 다릅니다.**
→ 통합 여부 확인 대상.

## ① 레거시 대비 (엑셀 변형 기준)

`매출일괄등록_모의고사.vb:438`:
```sql
DELETE salesData where left(tradeDate,8)='{0}' and catCode='{1}'
                   and tradeClass='모의고사' and tradeType='매출'
```
→ **일자+분류 단위 전체 삭제 후 재입력.** 트랜잭션이 없으므로
   INSERT 중 실패하면 **기존 데이터가 사라진 채 끝납니다.**

요구사항 `BE-24`("다건은 **비원자적 DELETE+INSERT**")가 실측으로 확정됐습니다.
35p 학교관리의 "전체삭제 후 재수입"을 발주처가 바꾸라고 한 것과 같은 패턴입니다.

**웹은 이 패턴을 쓰지 않습니다**(추가 등록 방식). 개선이 맞습니다.
