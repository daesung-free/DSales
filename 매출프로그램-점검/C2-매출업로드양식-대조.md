## ① 클라이언트 공식 양식 — 12열

```
거래일자 | 거래처코드 | 학교코드 | 분류코드 | 도서코드 | 회차
       | 정가 | 공급률(%) | 수량 | 금액(총금액) | 구분(출고유형) | 메모
```

샘플 행:
```
2026-06-30 | A10A195 | 10002 | S2026A02 | 01 | 4 | 36000 | 0.75 | 10 | 270000 | 정상출고
```

### 양식이 직접 적어 둔 규칙

| 컬럼 | 설명 (원문) |
|---|---|
| 거래처코드 | 매출프로그램 거래처코드 (거래처관리에서 조회) — **입력 필수** |
| 학교코드 | 학교/학원 등 세부 거래단위 코드 (학교관리에서 조회) — **입력 필수** |
| 분류코드 | (도서관리에서 조회) — **도서코드와 반드시 함께 입력 필수** |
| 도서코드 | ⚠ **분류코드마다 01부터 재사용되므로 분류코드 없이는 특정 불가** — 입력 필수 |
| 회차 | 세트 상품의 회차 (해당 없으면 0 또는 공란) — 선택 |
| 금액(총금액) | **정가 × 공급률 × 수량** 기준 정산 금액 — 필수 |
| 구분(출고유형) | 정상출고/위탁출고/증정용/교사용/반품/취소 중 선택 **(기존 출고등록 화면에는 없던 구분값으로 신규항목)** |
| 메모 | 원본 주문번호 등 참고 메모 — 선택 |

**검산**: `36,000 × 0.75 × 10 = 270,000` = 양식의 금액 ✓

## ② `uploadParse.ts` — 완전 일치 ✅

`src/features/sales/uploadParse.ts:9~14` 주석:
```
거래일자 | 거래처코드 | 학교코드 | 분류코드 | 도서코드 | 회차 | 정가 |
공급률(%) | 수량 | 금액(총금액) | 구분(출고유형) | 메모

- 분류코드+도서코드는 **함께** 필수 — 도서코드가 분류코드마다 01부터 재사용되므로
  분류코드 없이는 특정 불가.
```

**컬럼 순서·필수 규칙·경고 문구까지 양식 원문 그대로**입니다.

### 공급률 소수 표기도 양식 근거

양식 샘플: `공급률(%) = 0.75`

`uploadParse.ts:94`:
> 클라이언트 샘플이 **0.75(소수)로 와서** 둘 다 받습니다: `0<v≤1 → ×100`, `1<v≤100 → 그대로`

**샘플 파일을 실제로 보고 만든 구현**입니다. CLAUDE.md §4.6.15 의
*"12열 순서와 공급률 정규화(0.75 → 75)는 백엔드와 완전히 일치합니다. 바꾸지 마세요"*
가 **클라이언트 양식 원본으로도 확정**됐습니다.

### 거래처코드 형식도 확정

양식 샘플 `A10A195` → CLAUDE.md §4.6.16 의
*"DSRE2 실측 결과 매출코드는 **`A99A999` 7자 영숫자**. 기획서 34·35p 의 `10003` 은
**예시일 뿐**"* 과 일치. 학교코드는 `10002`(5자리 숫자)로 이것도 문서 기재와 같습니다.

## ③ 🔴 그래서 `/sales/bulk` 6열 양식은 근거가 없습니다

| | `/sales/entry` [파일 업로드] | `/sales/bulk` 매출일괄등록 |
|---|---|---|
| 양식 | **12열** | 6열 |
| 식별 | **코드**(거래처·학교·분류·도서) | 이름(거래처명·분류명·도서명) |
| 클라이언트 양식 | ✅ **일치** | ❌ **대응 없음** |
| 백엔드 계약 | ✅ `SalesUploadService` 일치 | ❌ 없음 |
| 근거 | 샘플 파일 실측 | *"기획서에 상세 양식이 없어 구조를 추론"* (코드 주석) |

`/sales/bulk` 는 **추론으로 만든 양식**이고, 08번에서 결함 3건이 나온 화면입니다
(금액 공식·마스터 대조·정가 하드코딩 — **전부 수정 완료**).

### 왜 이름 기반이 위험한가 — 양식이 직접 경고합니다

> ⚠ **분류코드마다 01부터 재사용되므로 분류코드 없이는 특정 불가**

도서코드가 분류코드 내에서만 유일합니다. 이름으로 찾는 6열 양식은 **동명 상품이 있으면
잘못 매칭**됩니다. 12열이 코드 2개(분류+도서)를 함께 요구하는 이유가 이것입니다.

### 권고

**`/sales/bulk` 을 12열 양식으로 통일**하거나, 최소한 **12열도 받도록** 확장.
지금은 사용자가 같은 「매출 일괄 입력」인데 화면마다 다른 양식을 써야 합니다.

## ④ ⚠️ 새로 발견 — 허용 출고유형이 양식과 다릅니다

**클라이언트 양식**:
> 구분(출고유형): **정상출고/위탁출고/증정용/교사용/반품/취소 중 선택**
> (기존 출고등록 화면에는 없던 구분값으로 **신규항목**)

**웹 구현** (`uploadParse.ts:37`):
```ts
const UPLOADABLE_SHIP_TYPES = ['정상출고', '증정용', '교사용'] as const
```
→ **위탁출고·반품·취소는 거부**합니다.

### 어느 쪽이 맞나

웹의 판단 근거(CLAUDE.md §4.6.15)는 탄탄합니다:
> 셋 다 **전용 절차**가 있고 업로드가 그 검증을 건너뛰기 때문입니다.
> - 위탁출고: 매출이 아니라 미결로 남았다가 위탁정산에서 확정되는 2단계 흐름
> - 반품: 기출고 잔여 범위 검증(`returns.ts`)을 통과해야 함
> - 취소: 원 매출을 지정해 되돌리는 처리
>
> 백엔드 `SalesUploadService` 도 **같은 계약**이고 레거시 `매출가져오기.vb` 도 같은 범위였습니다.

**레거시·백엔드·프론트 3자가 3종으로 일치**하고, 클라이언트 양식만 6종을 적었습니다.

→ **양식 문구가 실제 처리 범위보다 넓게 적힌 것**으로 보입니다.
   업로드로 위탁출고를 넣으면 미결 원장을 건너뛰어 매출이 **이중 계상**될 수 있습니다.

**확인 대상**: 클라이언트에게 *"양식에 6종이 적혀 있으나 위탁·반품·취소는 전용 절차가
있어 업로드에서 거부한다"* 를 회신하고 합의를 받아야 합니다. 지금은 **양식대로 넣으면
거부당하는** 상태라 사용자가 혼란스럽습니다.
